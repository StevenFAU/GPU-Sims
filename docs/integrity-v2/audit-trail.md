# Integrity Toolkit v2 — Audit Trail

> Companion to `toolkit-spec.md`. This document records how the spec
> was built and verified: methodology conventions, audit disciplines,
> probe records, banking decisions, retractions, and revision history.
>
> **Discipline.** New audit work accretes here. The spec doc absorbs
> the *substantive outcome* of audits (citation corrections, mechanism
> findings, fix-option recommendations) but does not carry the audit
> machinery itself. Banking rows, probe attributions, FACT/INFERENCE
> tags, and four-state verdicts all live in this document.
>
> **How to use these two docs together.** When dispatching a new
> audit probe: log its charter and report path in § 6 (probe registry).
> When the probe returns: file its substantive findings in § 5 (banking
> log) and apply *only the corrected content* to the spec doc. If the
> probe surfaces a new failure pattern, add a discipline section under
> § 4. If it surfaces an honest retraction, document it in § 7.

---

## § 1 — How to use these two docs together

There are two artifacts at `docs/integrity-v2/`:

| File | Purpose | Update rhythm |
|---|---|---|
| `toolkit-spec.md` | What the toolkit IS at v2.0. Architecture, categories, canonical references, implementation phases, design decisions. Forward-looking, declarative. | Converges — each revision approaches v2.0-complete. |
| `audit-trail.md` | How the spec was built and verified. Methodology, probes, banking, retractions. | Append-mostly — every probe adds a row; every rev adds to the changelog. |

**What goes in the spec.** Concrete spec content: a check's behavior,
a phase's commit plan, a canonical reference, a fix-option's tradeoffs,
a design decision's rationale. No "(per Probe X)" attributions in the
prose. The spec doc reads as if it has always been correct; it does
not record how it became correct.

**What goes in this doc.** Anything that begins with "Probe X found
that…" or "Rev N revised…" or "FACT-verified against…" or "INFERENCE
based on…". The audit trail explicitly carries provenance.

**The split is not absolute.** A probe finding that overturns a
fix-option in the spec causes both: (a) a banking row in § 5 here
recording the original claim, the refuting source, the verdict, and
the corrected statement; and (b) a substantive edit in the spec that
replaces the old fix-option text with the new one. The spec sees the
corrected text; this doc sees the audit trail.

## § 2 — Methodology conventions

### 2.1 Convention M — re-anchor before edit

> **Note on the rename (per Probe CCC § D.1 — banking row 84).** This
> rule was originally labeled "Convention K" through rev 15. Probe CCC
> found this collides with `conventions.md`'s actual Convention K
> (anchor-sketch labeling for spec content from inference — line 45 of
> conventions.md). The two rules are both legitimate and govern
> different lifecycle moments (CCC § D.1), so the audit-trail's rule
> moves to a new letter. Convention L is taken by the v2.28
> toolkit-source suppression hygiene proposal (spec § 1.7.R), so this
> rule becomes **Convention M**. To be formally banked into
> `tools/integrity/docs/conventions.md` at v2.0 commit 11 (renaming
> sweep + banking). All prior citations of "Convention K (re-anchor)"
> in this audit-trail and the spec refer to this rule and will be
> renamed in the same commit.

Before editing any cite, command, line number, or path: re-anchor by
reading the live source at HEAD. Never trust prior assertion of a
specific location — verify directly. Applies to every str_replace,
every commit message, every banking row.

This is the strongest convention in the project. Most fabrications
caught by probes share the same root cause: skipping the re-anchor.

### 2.2 Convention #8 — never assert specifics from memory

Specific numeric values, struct field names, function signatures,
CLI flags, or process patterns must never be asserted from memory.
Grep, view, or web-fetch before asserting. If grep is impractical
(e.g., a paper's author list), web-fetch the authoritative source.

The fabrication pattern targeted by Probe TT (§ 4.3 below) is the
strongest empirical case for this convention. Three of the four
REFUTED citations in the canonical-reference doc surface were
plausible-sounding 2nd-position-author confabulations that survived
multiple rev cycles because no one grep'd the underlying paper.

### 2.3 Convention #12 — SHA back-fill is a separate commit

Post-merge SHA back-fill of placeholder references in
`project-state.md`, landing memos, and audit reports must be a
separate follow-up commit, never `git commit --amend`. The amend
path was tried once and caught by Claude Code; the discipline is
now: substantive content → commit A → merge → SHA back-fill →
commit B.

### 2.4 Convention M addendum — design-rev persistence (new in rev 12; renamed from K in rev 16)

Every design-rev artifact (this doc, `toolkit-spec.md`) must land at
a stable repository path *before* any audit probe is dispatched
against it. Probe UU's first attempt could not execute because
rev 11 of the prior monolithic design doc lived only at
`/mnt/user-data/outputs/` — a non-persistent sandbox path invisible
to Claude Code. Stable paths:

- `docs/integrity-v2/toolkit-spec.md`
- `docs/integrity-v2/audit-trail.md`

Charters for probes that audit these docs must reference the
in-repo path, never the sandbox path.

## § 3 — Tagging and verdicts

### 3.1 FACT / INFERENCE tagging

Every concrete claim in a probe report or banking row must be tagged
**FACT** or **INFERENCE**.

- **FACT** — directly verified at the time of writing by reading the
  authoritative source (git history, file content at a specific SHA,
  paper PDF, DOI resolver response, runtime artifact).
- **INFERENCE** — plausible derivation from FACTs, but not itself
  directly observed. Inferences are useful but must be marked as
  such so future probes know which ground is solid.

A retraction (§ 7) typically takes the form "Probe X tagged INFERENCE
Y as FACT and that was wrong" or "Probe X tagged Y as FACT but the
authoritative surface was the wrong one."

### 3.2 Four-state verdicts

Audit findings use four states:

| State | Meaning |
|---|---|
| **CONFIRMED** | The claim is FACT-verified against the authoritative source. |
| **SHIFTED** | The claim is materially correct but a detail (line number, page reference, year, title) needs adjustment. |
| **REFUTED** | The claim is wrong — either fabricated or inverted. |
| **DEFERRED** | The probe could not reach a verdict (e.g., missing artifact, blocked tool, scope mismatch). Must be revisited. |

Two compound verdicts also appear:

- **DISCONFIRMED-AT-HEAD** — the claim was correct at the time it
  was banked but no longer holds at the current HEAD because of
  intervening commits. (Row 45 was originally tagged this way until
  Probe WW corrected the underlying baseline.)
- **REFRAMED** — the claim points at a real phenomenon but the
  framing it carried was wrong (e.g., the mechanism is different
  from what the original claim assumed).

## § 4 — Audit surfaces

### 4.1 Rev-doc-vs-HEAD audit (formerly § 0.7.A)

Each new design-rev is independently audited against the live
repository at the rev's anchor HEAD: every cite, line number, path,
and file existence claim is grep-verified.

Established by Probe GG (rev 8). Refined by Probes HH, KK, LL, UU.
Probe LL's rev 10 audit returned zero findings, marking the
discipline mature.

### 4.2 PP-pass — whole-doc self-grep discipline (formerly § 0.7.B)

For each substantive change applied to the design doc, grep the
*entire doc against itself* for the distinctive terms involved.
Catches drift that survives a section-local edit but lingers in
adjacent prose. Established by Probe PP (rev 10→11 cycle).

This is what would have caught the "80-130 commits across 14-18
phases" stale projection in rev 10 — it was inconsistent with the
"Phase 11 expansion" content elsewhere in the same doc.

### 4.3 Canonical-reference-doc-vs-source audit (formerly § 0.7.C)

For every paper / textbook / external artifact cited in a
canonical-reference doc (sim-spec, category-context, load-bearing-
decisions), verify the citation verbatim against the authoritative
source: DOI resolver, journal page, PubMed, ACM DL, Eurographics
DL, ADS, NTRS, author homepage.

Established by Probe SS (rev 10→11 cycle) after quantum.md was
found to harbor a fabricated parenthetical co-author claim that the
prior § 0.7.A discipline could not catch (the fabrication was one
level *upstream* of the design doc and rev-doc-vs-HEAD audits never
read the canonical-reference docs themselves).

**Failure pattern (post Probe TT):** the byline-confabulation
surface has three known sub-variants:

1. **Substitution** — a real 1st author + a fabricated/substituted
   2nd-position name. Examples: Harris-King 2018 (King not on
   paper); Vodeb-Verstraelen 2025 (real 2nd author is Desaules);
   Müller-Fetterer 2007 (real 2nd author is Schirm).
2. **Omission** — a real paper cited with truncated author list
   dropping the 2nd-position author. Example: Mordvintsev "Distill
   Neural CA" without Randazzo, Niklasson, Levin.
3. **Entire-paper-fabrication** — the cited paper does not exist;
   the closest real referent has different authors/title/year.
   Example: "Williams, van der Laan 2008" — real referent is
   van der Laan, Green, Sainz 2009 "Screen Space Fluid Rendering
   with Curvature Flow."

The discipline catches all three via a verbatim 2nd-position-author
check against an authoritative resolver.

**Proposed integrity-toolkit check (queued for spec):**
`cat1.byline-verify` — for each citation registry entry with a DOI
or arXiv id, fetch the canonical author list from the resolver and
compare verbatim against the in-tree citation. Mechanical, would
catch all four REFUTED entries automatically. Per Probe TT § H.2.

### 4.4 Auxiliary-vs-authoritative surface discipline (new in rev 12)

When claiming a thing-does-not-exist or a thing-does-not-fire,
verify against the **authoritative** surface, not an **auxiliary**
one. Two instances of this failure pattern were caught in rev 12:

1. **Probe NN's cat1.bare-path "0 HARD_FAILs at HEAD" claim
   (corrected by Probe WW).** Probe NN ran
   `python3 -m integrity --check cat1.bare-path --root project-state.md`
   and observed `1 pass, 0 hard-fail`. The `--root` flag with a
   single-file argument produces a vacuous "1 pass" result rather
   than a real per-file check — this is auxiliary output, not
   authoritative. Probe WW ran the toolkit at full repo scope
   (the authoritative surface) and found 6 HARD_FAILs on
   project-state.md, exactly matching Probe N's original banking.

2. **Mid-rev-12 SPlisHSPlasH "no 2.16.x release exists" claim
   (corrected by Probe XX).** Reading the GitHub Releases page
   (manually-curated announcement objects) showed only 2.15.0 as
   the latest, and an unsafe inference from "no Release object" to
   "no git tag" was made. The git tag set is the authoritative
   surface; Releases is auxiliary. Probe XX bare-cloned upstream
   and verified the `2.16.1` tag exists, points at the in-tree
   SHA, and is current master HEAD.

**Discipline.** For non-existence claims:
- Git tag set, not GitHub Releases.
- Full-repo toolkit invocation, not `--root <single-file>`.
- DOI resolver / PubMed canonical metadata, not journal-preview
  snippets.
- Author list directly from publisher page, not the SciRP /
  bibsonomy mirrors (which sometimes shorten or reorder).

project-state.md; rev 10's banked 6 findings must have been cleared
by an intervening commit, likely `ebbb743` ("remove project-state.md
fossil annotations").

**FACT (Probe WW direct verification):**
1. ebbb743's diff on project-state.md deletes only 3
   `cat1.intra-repo` annotation comments, not bare-path citations.
2. ebbb743's commit message explicitly states "5 HARD_FAILs continue
   to fire."
3. At HEAD, the toolkit reports 6 HARD_FAILs on project-state.md
   (lines 561/594/686×3/741), exactly matching Probe N's original
   banked set.

**What happened.** The `--root <single-file>` flag invocation in
Probe NN's command does not check the file the way `--root <repo>`
does at full scope. It produces a vacuous "1 pass" output that
Probe NN misread as "0 findings." The vacuous-pass behavior itself
is one of the items v2.0 commit 3 (fail-open fixes) addresses.

**Lesson.** Toolkit output that comes from a non-canonical
invocation is auxiliary, not authoritative. For checks at HEAD,
the authoritative surface is the full-repo invocation.

### 7.3 Mid-rev-12 SPlisHSPlasH "no 2.16.x release" → Probe XX correction

**Original claim (mid-rev-12 web research):**
Reading `github.com/InteractiveComputerGraphics/SPlisHSPlasH/releases`
shows the latest *Release* is 2.15.0 (Aug 12, 2025). Inferred from
this that no 2.16.x git tag exists upstream and that the in-tree
"2.16.1" version label may not correspond to any real upstream tag.

**FACT (Probe XX bare-clone of upstream):**
- `git cat-file -t 6bff55a6...` returns `commit`.
- `git tag --contains 6bff55a6...` returns `2.16.1`.
- `git describe --tags 6bff55a6...` returns `2.16.1`.
- The SHA is current `master` HEAD as of 2026-05-12 (author: Jan Bender).
- The in-tree `references/SPlisHSPlasH/` is a detached-HEAD git
  checkout at exactly the same SHA, working tree clean.

**What happened.** GitHub *Releases* (manually-curated announcement
objects) are not the same as git tags. The maintainer had tagged
2.16.1 but had not yet published a corresponding Release entry. An
unsafe inference from "no Release" to "no tag" was made — the tag
set is authoritative.

**Lesson.** For non-existence claims about published software
versions, the authoritative surface is the git tag set on the
canonical repository, not the publisher's release-announcement
page.
